SPI Code visual design

The window as an app for three uses: view the program, act on it, and chat about it. The information architecture, navigation, layout and interaction model, with the Shore palette and the component kit.

Product brief Product requirements Visual design (this page) Original combined design (PDF)

The first window built for M2 is the keelson-rib-spi console inside an app shell. Six report pages (Today, Repositories, Releases, Environment, Flow, Horizon) each re-slice the same world, so one stopped service appears in four shapes and the operator joins them in their head. Each page carries its own detail pane beside the right-panel inspector, and the two drift apart. Evidence chips repeat three to five times per page. The tree is a list of page links: every service routes to Flow, there is no page for one service, and the Runs section is bare run ids. Nothing in the layout has a place for acting on the program or for a thread with Copilot.

This design organizes the window around things (a service, the template, the environment, a release month) and work (the Inbox, approval cards, threads), not pages. The sidebar lists them. The middle shows one list, one thing, or one thread. The right panel is the one detail surface for whatever is selected, with the selection's evidence behind a tab. Actions live on the detail and create cards; threads start from a thing and stay anchored to it. The sweep's health is one sentence in the title bar.

Core, the host, the sweeps, the Watch contract and the model's output do not change: every text the window draws still comes from the same core functions the rib renders, so the M2 parity check stays data-level (Parity with the rib). Four values the new layout wants and the contract does not carry are named as contract additions, not assumed (Contract additions). Use B (act) and use C (chat and code) get their places here and are built in M3 to M5; this page does not specify their behavior beyond placement and interaction. Mockups are drawn proposals with example names, counts and numbers.

Window anatomy

Five regions. The sidebar chooses what the middle shows; one selection in the middle drives the right panel; the terminal drawer exists only in code threads.

These rules hold everywhere:

  • The middle shows one thing. It never carries a second copy of the selection's detail; the right panel does that.
  • One selection, one panel. Selecting a row, a station, a release month or an event fills the right panel. Navigating to a new place clears the selection unless the new place contains it.
  • Evidence is shown once per surface: one line in the title bar for the sweep, one line on a section whose sources are not fresh, one tab for the selection. No chip rows.
  • A thread starts from a thing and names it. The composer exists only in a thread and always shows the anchor.
  • A button never writes; it creates a card. A disabled action states why, in place. Before M4 every write action is disabled with the reason that writes arrive at M4.
  • Color never carries meaning alone. Every dot has a word beside it, every priority is written P0 to P2, every evidence state is a word.
  • Nothing opens a modal except ⌘K.

On macOS the title bar uses hiddenInset with the traffic lights inset, and on Windows a hidden title bar with titleBarOverlay, as T3 Code's apps/desktop/src/window/DesktopWindow.ts getWindowTitleBarOptions does. The first window used a 34 px bar; this design uses 40 px so the sweep line and the place fit beside the traffic lights.

Navigation model

Three kinds of place, and three ways to move between them. The rule that keeps the window small: a thing has a page, a list has rows that are things or items, and a lens is a list whose rows are the same things seen through one concern. A pull request, an issue, an alert, a run or a queue item is never a page. It is a row on the thing it belongs to, and the right panel describes it when selected.

Lens tables sort by any column and keep the sort per lens. A row stays selected while the operator moves between a lens and the service page it opens, so the right panel does not blank out on the way. Group headings in the sidebar collapse and remember it, and the Services group shows all 13 lines rather than five and a fold: the operator's day is spent on these names, and the sidebar scrolls.

Inbox

The Inbox is the default place and the operator's day. It carries what the rib's Today carries, in the same order from the same briefing: headline, summary, three facts, the queue in P0, P1 and P2 order, and the ready line. Two things are new. Each row names its scope with a chip that opens the thing's page, so the queue is the way into the rest of the window. And a Waiting for you section sits above the queue; it holds pending approval cards from M4, and the Inbox count in the sidebar and title bar adds them to the P0 and P1 items. Before M4 the section says that cards arrive at M4.

Program pages

The three program things each have a page with the same shape as a service page: a headline, facts, sections, and the right panel for the selection.

  • Template. The template fact (version on main, how many forks are on it), the rollout in progress as a queue row with the rib's detail lines, the forks with the template version each runs (a contract addition; the fact carries fleet counts only), and the template repository's open work.
  • Environment. The rib's Environment view without its in-page pane: headline, three facts, the last 24 hours as the four lanes on an hour track, the fork-lanes note, the stack repository's open work, and a Live cluster section that stays empty until M6 and then labels live reads apart from the workflow-run inference above it (PS-07). Selecting an event fills the right panel.
  • Releases. A list of months, newest first, each with its notes state and headline. Selecting a month shows its figures; opening it shows the month's page with the stats, key changes and the release document.

Lenses

A lens is a dense, sortable table across the fleet for one concern. The four lenses carry the rib's Flow, Repositories and Horizon views and a new Runs table, without the in-page panes the rib drew beside them. The rib's lone "·" placeholder cells are drawn blank. Selecting a row fills the right panel; opening a row goes to the thing's page.

Right panel

The right panel describes the selection and nothing else. It has three tabs in a fixed order. Detail is the inspector: class, title, cause, effect, next, the actions the item offers with the reason under any disabled one, then Ask and, where PB-03 applies, Fix in a code thread, then the item's evidence links. Evidence lists each area the selection draws from with its state, age and completeness in plain words, then the reads for the selection's repository. Log lists the selection's runs from M3 and is drawn disabled before that. A selection that no thread owns shows the two thread buttons; one a thread owns shows the thread instead (TH-05), as the box under the title in the Inbox mockup.

The panel has no Approvals tab. Pending cards are work, so they wait in the Inbox under Waiting for you, and a card asked for inside a thread is decided in that thread's composer strip. The right panel shows a card's detail when the card is selected, like any other row. A card has one id and one state in the host's approval store, appears wherever it is relevant, and is decided in one place per origin (AU-09, AU-10).

In a code thread the context tabs are Changes and Checks in place of Detail and Evidence: the worktree, its changed files, the target branch, and the required checks at the pushed commit. Log stays. T3 Code's RightPanelTabs.tsx and ChatRightPanel.tsx are copied for the frame; rightPanelStore.ts is ported down to the selection and each context's chosen tab.

Threads

A thread is the home of use C. It starts from a thing: Ask on the Detail tab, a sentence typed into ⌘K, the + beside Threads, or Fix in a code thread. Its header names its kind and its anchor, and the first entry in the timeline is the context line: the anchor's reading and the sweep time it came from (TH-02). The composer sits under the timeline and always shows the anchor chip. Threads list newest first in the sidebar; a code thread carries a filled square marker in the agent color.

Parity with the rib

The M2 check is data-level and stays achievable. The parity suite (bead t1k.59, PS-02, PS-04, PS-05) compares three things: the host's projected Briefing object and the Releases pane input against the rib oracle from one recorded sweep; the inspector result per class against the oracle after the documented mapping; and the window's rendered text for each view against the oracle text. The first two do not touch the window and are unchanged by this design. The third changes shape, not substance: the rib's six views become surfaces that own the same briefing fields, and the window test asserts each field's text once, on the surface that owns it, with the rib's "·" placeholder cells mapped to blank.

What changed from v1 and why

The first visual design put the rib's six console views in the middle panel behind a tab row, with a composer under every view and an Approvals tab in the right panel. The maintainer's review of the window built from it found the problems in the box at the top. This table is the change list; the one after it is the alternatives considered on the way and not taken.

v1v2Why
A tree of page links: Today, System, Stack, Services (Flow, Horizon, then lines), Threads, Runs, SetupA sidebar of things and work: Inbox, Program, Services, Lenses, Threads, SetupEvery tree entry routed to one of six pages; a service entry opened Flow. Things need pages and work needs a queue.

AlternativeWhy not
Keep the six pages and remove the duplicate panes and chipsThe pages would still re-slice one world four ways, and a service would still have no page. The review's first finding was the shape, not the trim.
