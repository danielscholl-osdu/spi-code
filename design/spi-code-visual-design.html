SPI Code visual design

The window, the Shore palette in semantic roles, and the component kit, with the T3 Code or Keelson source each piece is built from.

Product brief Product requirements Visual design (this page) Original combined design (PDF)

The program is read today through the keelson-rib-spi console, which draws boards inside Keelson's own window, and through a terminal. The original combined design sketched an SPI Code window in two mockups. Its inspector gave the wrong fix path for a Prove failure, it had no dark or code-thread view, and several of its light-mockup text colors fell below WCAG AA contrast.

This document sets the window's layout, the colors and their jobs, and the components the requirements name. The structure comes from T3 Code: its three-pane layout, right-panel tabs, approval strip, work log and terminal drawer, and its semantic theme roles. The colors come from Keelson's Shore palette, with darker text variants where Shore's light values are fills. Each piece names the file it is copied from, ported from or modeled on, so the window can be assembled from working code.

Every mockup on this page is a drawn proposal, not a screenshot; names, counts, SHAs and PR numbers are examples. It does not specify icons glyph by glyph, motion timing or the onboarding copy. The contrast figures are computed from the hex values with the WCAG 2 formula; no built window has been measured.

Window anatomy

The window has five regions. A console view or a thread fills the middle; the left tree chooses what the middle shows, and the right panel describes the selection in the middle. The terminal drawer exists only in code threads.

These rules hold in every view:

  • Reading happens in the middle panel on the card surface, the lightest one in the light appearance. The tree, title bar and right panel use the chrome surfaces around it.
  • One selection drives the right panel. Selecting a queue row, a fork or a run fills the inspector; nothing opens a modal.
  • Every view states the sweep time and whether every source was read, in the view tab row.
  • The composer always shows its anchor, so the operator knows what context Copilot starts from.
  • A disabled action states why, in place.
  • Color never carries meaning alone. Priorities are written as P0, P1 and P2; card states and evidence chips are words.

On macOS the title bar uses hiddenInset with the traffic lights inset, and on Windows a hidden title bar with titleBarOverlay, as T3 Code's apps/desktop/src/window/DesktopWindow.ts getWindowTitleBarOptions (line 235) does. Its heights there are 52 and 40 pixels; SPI Code's are not set yet. Below a window width of 980 pixels the right panel becomes a popover, using T3 Code's RIGHT_PANEL_INLINE_LAYOUT_MEDIA_QUERY from apps/web/src/rightPanelLayout.ts, and the tree can collapse to T3 Code's 3rem icon rail (ui/sidebar.tsx SIDEBAR_WIDTH_ICON, line 30).

Today

Today is the default view. It shows the briefing headline, three fact tiles, the focus queue in P0, P1, P2 order, and the ready line. The selected row fills the inspector. This mockup corrects the original's inspector, which sent a Prove failure to fork_integration; a Prove failure on the open release PR is fixed on that PR's head branch (product requirements, Code threads).

The row shape, the selected state and the collapse behavior come from T3 Code's Sidebar.tsx and ThreadStatusIndicators.tsx. Both import Effect and are built around projects and chat threads, so they are ported. The ui/sidebar.tsx primitive is copied.

Right panel

The right panel's tabs come in a fixed order: the context tabs for what is selected, then Approvals, then Log. On a console view the context tab is Inspector. In a code thread it is Changes and Checks. Approvals is one inbox for every pending card in the app, and Log is the selected object's runs and the sweep's read history for it.

A card has one id and one state, held in the host's ApprovalStore, and appears wherever it is relevant. It is decided in one place per origin. A card requested in a thread is decided in that thread's composer strip, and its timeline row and inbox row point there. A card requested by a button is decided on the card itself. A button never writes; it creates the card. The card states are drawn in the product requirements, Authority, tiers and approvals.

T3 Code's RightPanelTabs.tsx and ChatRightPanel.tsx import no Effect and are copied. rightPanelStore.ts (1,258 lines) is ported down to the selection and each context's chosen tab, which is all the window keeps itself.

Code thread

A code thread works in a worktree on one fork branch. Its header names the local branch, the remote target, and the base and head. The timeline interleaves the operator's messages, Copilot's replies, work log entries and cards. A pending card sits in the composer strip. The drawer has two tabs: the read-only record of approved commands, and the operator's own login shell, labeled as outside the sandbox.

Shore in semantic roles

SPI Code has one palette, Shore, in a light and a dark appearance. The appearance follows the system unless Settings pins one; there is no palette picker. Components never name a hex value or a Shore key. They name a role, following T3 Code's role model in packages/shared/src/themePalettes.ts (THEME_COLOR_ROLES, line 30), cut down to the roles this app uses. T3 Code has error, warning and update roles but no success role, so SPI Code adds one. It also adds an agent role for Copilot's words.

Shore's light accent, red, yellow, green, magenta and dim values work as fills, dots and borders, but all six fall below 4.5:1 as small text on at least one light surface. Each such role gets a darker text variant in the light appearance; dark Shore values pass as text and are used unchanged, except dim, which is lightened. Appendix B has the computed ratios. A filled badge or primary button puts the light-appearance text variant behind white text, and the dark value behind the dark chrome color.
