SPI Code visual design

T3 Code's workbench with SPI awareness: the program's state drawn in the window, acted on through cards, and handed to Copilot as structured context instead of re-read from GitHub.

Product brief Product requirements Window design Visual design (this page) Original combined design (PDF)

The window design wins where this page disagrees with it. That covers this page's layout, its page table and its PS-02 parity table (Parity with the rib), which the requirements replace with reachability. The palette and the component kit on this page stand.

The first window built for M2 is the keelson-rib-spi console inside an app shell. Six report pages re-slice the same world, each with its own detail pane beside the right-panel inspector, evidence chips repeat three to five times per page, the tree is a list of page links, and nothing has a place for acting on the program or for a thread with Copilot. The window was a dashboard with a chat box waiting to be bolted on.

This design makes T3 Code's workbench the base and the SPI views a layer in it. The base is threads under their things in the sidebar, a timeline and composer, a right panel with the worktree, branch, changes and checks, the terminal drawer, worktrees, approvals and the model picker. The SPI layer is the sweep line, the Inbox, a page per thing, three lenses, and the Detail and Evidence tabs. A bridge joins them: every thread has one anchor, any selection becomes a context chip in the composer, every write is a card, and a thread's status and artifacts show on the thing it works on. The view exists so the operator and Copilot see state instead of fetching and narrating it.

Core, the host, the sweeps, the Watch contract and the model's output do not change. The M2 parity check stays data-level, taken per owner surface with mirrors listed (Parity with the rib). Five values the layout needs and the contract does not carry are named as additions and are a hard predecessor of the surfaces that need them; no M2 surface ships on a placeholder (Contract additions). Use B (act) and use C (chat and code) get placement and interaction here and are built in M3 to M5. Every name, count and sentence in a mockup is an example, not a reading of the live program.

Layering

Three bands. The base is T3 Code's workbench, ported or copied component by component (appendix A). The SPI layer sits on it and draws from the Watch contract. The bridge is the small set of objects that cross between them, each with one owner.

T3 Code's sidebar is projects, each holding its threads. SPI Code's sidebar is things, each holding its threads: a service row, and each Program row, expands to the threads anchored to it, with the thread's status and, for a code thread, its worktree branch under the title, as T3 Code draws it. Threads with no anchor sit under the Inbox. Settled threads fold into one Settled shelf at the bottom of the sidebar with its count, as in T3 Code; the shelf opens on click and ⌘K finds any thread by title. The window lands on the Inbox at M2; from M3 it lands on the last open thread, or the Inbox when there is none.

Window anatomy

  • The middle shows one thing. The right panel is the one detail surface; no page carries a second copy of the selection.
  • One selection, one panel. A selection is an id. It survives navigation when the destination lists that id as a row, a station, a line or a thread's anchor; otherwise it clears. Returning to a list restores its scroll position and selected row; the window keeps one position per route. While ⇧ holds several rows, the right panel shows the Detail of the last row selected under a line that counts the selection, and Add to chat takes them all.
  • Evidence is shown once per surface: the sweep line, one line on a section whose sources are not fresh, one tab for the selection.
  • A thread starts from a thing and names it. The composer exists only in a thread.
  • A button never writes; it creates a card. A disabled action states why, in place.
  • Color never carries meaning alone. Every dot has a word, every priority is written P0 to P2, every state is a word.
  • Nothing opens a modal except ⌘K.

Navigation model

A thing has a page, a list has rows that are things or items, and a lens is a list whose rows are the same things seen through one concern. A pull request, an issue, an alert, a run or a queue item is never a page: it is a row on the thing it belongs to, the Detail tab describes it when selected, and @ in a composer attaches it.

Inbox

The Inbox is the operator's day and the M2 landing place. It carries what the rib's Today carries, in the same order from the same briefing. Each queue row names its scope with a chip that opens the thing's page, and a row a thread owns carries that thread's marker. Waiting for you lists every pending card with the thread or button that asked for it. A thread's card is decided in that thread's composer strip and its row opens it; a button's card is decided on its row here and nowhere else. Detail and runs show a card's state and link here (AU-10). The Inbox's sidebar pip is one combined total of P0 and P1 items and pending cards, shown nowhere else; the section counts inside the Inbox are labels on their lists, not that total.

Context hand-off

The reason the view exists beside the chat: what the operator sees is already a reading, so it goes to Copilot as data, not as a request to go and read GitHub. A context chip is one selection packed for a thread. Chips are added by @ in any composer (a service, a queue item, a line, a run, a lens row, a theme, or a file in a code thread), by Add to chat on the Detail tab or the toolbar (⌘⇧A), and by selecting several rows with ⇧ and adding them at once. A chip can go to a new thread (Ask) or to an existing thread of the operator's choice, defaulting to the thread that owns the anchor. In the composer a chip is a draft: preview, remove and refresh act on drafts only. Sending snapshots each chip's exact payload, sweep time and evidence onto that message, and a sent chip never changes.

A chip carriesWhich is
IdentityThe stable id, kind and title; the scope (service, program thing) and, for lines, the URL once the contract carries it
The readingThe compact inspect result: class, cause, effect, next, why, the action ids with their disabled reasons, related ids
Its evidenceThe read records behind it (source, object, observed at, inferred, completeness) or, when the result predates per-value provenance, the evidence references it lists
Its freshnessThe sweep time it came from, the provenance areas with their states, and completeness in the words the Evidence tab uses
By kindWhat the Detail-by-kind table gives that kind: the inspect result for every kind with an id, themes and environment events included; a station's label, state, text and upstream inspect. A repository line cannot be a chip until it has an id
NeverRaw pages, logs, diffs or issue bodies. Copilot fetches those with read tools if it needs them, and the work log shows that it did

Proposed. The composer carries the anchor and three chips; clicking a chip opens its preview with the exact payload, a raw view, a refresh from the latest sweep, and remove. A draft from an earlier sweep is dimmed and says so until refreshed; a sent chip keeps the sweep it was sent with.

Budget: a chip is at most 2,000 tokens and a message at most 8 chips. A chip over budget is trimmed to identity, class, cause, next and evidence references, and its preview says "trimmed". The seeded message is the structured payload, sent the way T3 Code sends context references on a user message and drawn in the timeline as the same chips (TH-02, PS-14). A thread has exactly one anchor and any number of attachments over its life (TH-01).

Threads and the return path

A thread lives under its thing. Its header names its kind, its anchor and, for a code thread, its branch. The first timeline entry is the context line. Threads are listed with T3 Code's statuses: Working, Waiting on you (an open card, a question, or a push to review), Done, Failed, Stopped; Done, Failed and Stopped threads are Settled and move to the shelf. The same status shows on the thing's sidebar row and in the Threads section of its page, and a queue row a thread owns carries that thread's marker (TH-05).

What a thread makes comes back to the view. The host's thread store records every pull request, run or issue a tool call created, keyed by the URL or run id the tool result returned, with the thread and the time. Nothing is recorded before it exists: a proposed push or PR lives on its card, and a branch, which has neither URL nor run id, appears on the Thread tab only. The window joins snapshot rows to the store by key, so a PR a thread opened shows the thread's marker on the service page and in the Repositories lens. Until a sweep has read the object, the row is drawn from the store, dashed, and says "pending · not yet in a sweep"; when a sweep row matches the key, it is drawn solid and sweep-confirmed, and the dashed row is dropped. This is a window-side join, not a contract addition; it needs the repo-line ids and URLs already listed as an addition.

Code threads

A code thread is T3 Code's coding thread on a fork worktree. Its right panel leads with the Thread tab, which is T3 Code's thread details card with SPI Code's cards in place of direct git writes: environment and worktree (this machine, the worktree path), Open in editor, branch and pull request (the thread's branch, its target, the PR with its status once it exists), git actions (Commit and Push, each making a card), Changes against the target with +/− counts per file that open the diff in the middle panel, Checks at the pushed commit, and lineage (the thread it started from, delegated agents). The anchor's Detail and Evidence stay as tabs, and the same tabs are in the sheet below 980 px. The terminal drawer has two tabs here: Approved commands, read-only, and the login shell. Every thread has the drawer at M3 because T3 Code has it everywhere and the login shell is the operator's own; only code threads have commands to show in the first tab.

Right panel

The right panel describes the selection and nothing else. Outside a thread it has Detail, Evidence and Log. Detail is what the kind table above allows: the inspect result where there is one, the row's own fields where there is not, the actions with the reason under any disabled one, then Ask, Add to chat and, where PB-03 applies, Fix in a code thread, then the evidence links. A selection a thread owns shows the thread and its status instead of Ask (TH-05). Evidence lists each area the selection draws from with its state, age and completeness in words, then the reads for its repository. Log lists the selection's runs from M3. In a thread the Thread tab leads, with the anchor's Detail and Evidence beside it. There is no Approvals tab: cards are work and wait in the Inbox.
