SPI Code Threads

How SPI Code gets AI threads like T3 Code's, with the 13 services, the template and the stack in place of user-made projects, with Copilot told what the operator is looking at, and with its tools in a sandbox.

SPI Code reads the program well and can't yet talk about it or change it. The host streams one Copilot turn through the SDK, but there is no thread, no composer and no checkout of any repository, and all 53 agent tools are stubs.

This design adds threads on SPI Code's own engine, in the host, on the Copilot SDK it already runs. The engine is a package with no SPI Code imports, so another app can use it. T3 Code supplies the behaviour and the look, re-made in SPI Code's kit, and none of the code. In place of T3 Code's projects there is a fixed set of scopes (the program, each service, the template, the environment). Each service has one clone that holds both its GitHub fork and its GitLab upstream. A Lands in choice decides whether a change becomes a fork pull request or an upstream merge request. Copilot is handed the place or row the operator started from as packed context, plus read tools over the last sweep.

It changes one PRD rule: Copilot gets its built-in shell and file tools. They run inside the SDK's sandbox, without the operator's sign-ins, and each edit or command waits for approval. Copilot can't commit, push or open a request; the operator does, from the thread. The sandbox has been run on macOS only. On Windows Server 2025 in CI, MXC found no ProcessContainer, so a Windows thread asks and reads. Program operations (dispatch a cascade, re-run a lane) stay typed tools with cards, as M4 has them.

Scopes in place of projects

T3 Code binds a thread to one project, and a project is one folder the user added. SPI Code has no projects to add. A thread has a scope, picked from a fixed list that SPI Code seeds from the fleet it already reads: the program, the 13 services, the template and the environment. That is 16 scopes. The engine sees each as a project whose folder SPI Code owns under app data; the operator never sees the word project, a folder picker or a clone dialog.

The scope comes from where the thread starts: ⌘N asks for it in the scope picker, a service page's Ask gives that service, Template and Environment give theirs, and Ask about this gives the row's fork or Program. The draft's Ask in control changes it before the first message. After that it is fixed, because the engine's worktree and history belong to one folder.

A program thread reads across everything and changes nothing. When its answer leads to a change, it offers the scopes involved, and choosing one starts a child thread there that carries the finding. The Thread tab shows the lineage.

A fork and its upstream share history through the fork's upstream branch, which is what lets one clone hold both. A scope's repositories are cloned on first use and the clone shows as the first row of the timeline, the way T3 Code shows worktree setup. Nothing is cloned for a scope the operator never opens a thread in.

Where a change lands

In a service, some code is OSDU's and can only change through a merge request upstream, and some is the fork's provider code and changes through a pull request on GitHub. T3 Code's branch toolbar asks for a base branch and an environment mode. SPI Code replaces it with one choice, Lands in, whose options are the only destinations a change in that scope can have.

A thread starts on Asking unless it starts from something that names a branch. An existing pull request or merge request is a fifth case: the thread is prepared on that request's own branch. An asking thread moves into a worktree later through the same chip, so the operator does not have to decide before the question is answered.

The owner tag on a changed file

The Changes list tags each file fork or upstream. When a file's owner does not match where the thread lands, the row says so and offers to redo that file in a thread that lands in the right place. That opens a draft naming the file; the change stays in this thread until carrying it across is built (spicode-1rj7). The same sentence goes to Copilot in its instructions, with the scope's ownership rule, so it proposes the split itself. The tag is a warning and blocks nothing: the operator can still commit an upstream-owned file to the fork.

Core already separates SPI code from upstream code for security alerts. The tag needs that rule exposed per path. Until core can classify a path, the file carries no tag and no warning, never a guess.

Where an upstream push goes depends on the operator's GitLab access. A maintainer pushes a branch to the upstream project. Anyone else pushes to their own fork of it on GitLab, which the clone holds as a third remote, and the merge request goes from that fork into upstream. SPI Code reads which applies with glab when the thread first lands in Upstream and names the remote on the Thread tab. It does not create a fork: when the operator has neither, the Thread tab says so and links to the upstream project.

What Copilot is told

T3 Code tells its agent the folder and the user's message. SPI Code adds three layers so the operator never has to describe what is on screen.

LayerWhat it carriesWhenHow it travels
Scope instructionsThe scope's repositories and remotes, the branch model (upstream, sync, integration, main), which paths the fork owns, where each kind of change lands, and that SPI tools answer program questions faster than re-reading GitHubEvery threadThe session's instructions, resent only when they change

The packed chip is what the host's inspect already returns for a row or popover, so no new reading is written for it. The SPI tools return the snapshot and say when it was read. For anything deeper, Copilot reads the code in the thread's folder and runs git there, and the work log shows each call. gh and glab have no sign-in inside the sandbox, so a fresher read of GitHub or GitLab is an SPI tool the host answers.

SPI tools read only. Program operations that write (dispatch, re-run, merge) are not offered in this change and arrive with M4 as tools that raise a card.

When a thread already owns a row, the control reads the thread's title and status and opens that thread, as TH-05 has it.

Threads in the sidebar and on a service

The sidebar lists threads by status under Pinned, as PS-08 already draws: Waiting on you, Working, then the Settled shelf with its count. This is also how T3 Code's sidebar groups them. Each row adds its scope at the end in muted ink, and a thread with a worktree shows its branch and target under its title.

A service page gains a Threads tab after Security, with the count of threads that are Waiting on you or Working. It lists every thread scoped to that service, settled ones under a fold. Template and Environment list theirs under their reading. Threads are not nested under a pinned service in the sidebar.

How it runs

Threads run in SPI Code's own host, on the Copilot SDK session the host already starts. The engine is a new package, @spi-code/threads, that imports nothing from SPI Code. The host hands it four things: where a thread works, which tools are offered, the instructions and context, and the channel its events travel on. Another app can supply its own four and use the same engine and view.

T3 Code is the source of the thread's behaviour and look, not of its code. Its server is about 303,000 lines written in Effect, and its web app is not a package that can be mounted. The table says what is re-made from it in SPI Code's kit and what is not carried.

Authority

Copilot has its own shell and file tools in a thread that lands somewhere, and every one of them runs inside the Copilot SDK's sandbox. The engine sets the policy; the operator's approval decides whether a call runs at all. The sandbox was run on macOS on the prototype. Appendix D has each check.

Inside the sandboxPolicySeen on macOS
Files writtenThe thread's worktree and a temp folderA write anywhere else fails, by shell and by file tool
Files readThe worktree, the clone and the toolchain foldersReads are denied unless granted. The home folder, ~/.ssh and ~/.config/gh can't be listed
The clone's git folderWritable, with its hooks and config read only (CT-08)A commit works; a hook or config write fails. The default policy alone leaves both writable
NetworkGitHub, the OSDU GitLab and the package registries a build needsAn allowed host answers; any other fails, also when the proxy is skipped
EnvironmentAn allow-list with no token variables (CT-09)The sandbox does not filter the environment, so the engine starts the runtime with a cleaned one
Leaving the sandboxNot offeredWith bypass off, a blocked call fails and raises no request

Three rules follow from what the probe found. The engine supplies the policy on every create and resume, because a session resumed without it runs unconfined and says nothing. Before each turn it reads the runtime's sandbox state, and a thread whose sandbox is not engaged offers no shell or file tools (CT-07). An approval is never granted by its kind alone, because a request to leave the sandbox arrives as an ordinary write request with a flag.

ActionWho does itControl
Read files, search codeCopilot, in the worktree or the shared cloneThe sandbox's read paths. No prompt
Edit a fileCopilotAn approval row with the diff in Supervised; no prompt in Auto-accept edits
Run a command (build, test, git)Copilot, in the sandbox, with no sign-inAn approval row with the command, every time
Read GitHub or GitLabThe host, through SPI toolsTyped read tools. gh and glab have no sign-in inside the sandbox
Commit, push, open a PR or MRThe host's own git, gh and glab; add and commit confined under @microsoft/mxc-sdk, push outside the sandbox (CT-11)The operator presses it on the Thread tab. Copilot cannot
A program operation (dispatch, re-run, merge)The hostA typed SPI tool that raises a card, M4, unchanged

A command the host runs itself, such as a fork's build or verify script (CT-16), is not a Copilot tool and the SDK's sandbox does not cover it. Those run under @microsoft/mxc-sdk with the same policy. The Copilot runtime's sandbox is that same library, so one policy format serves both. It takes the place of the hand-written Seatbelt profile and Windows restricted token in CT-07.

Windows is not proven. Until the same checks pass there, a Windows thread asks and reads and offers no shell or file tools.

What the prototypes showed
