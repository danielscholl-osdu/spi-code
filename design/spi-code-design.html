spi-code · desktop operator app · design

SPI Code

A macOS and Windows desktop app for running the SPI program (System, Stack, Services) with GitHub Copilot as its only agent, built on the SPI domain already proven in keelson-rib-spi.

Operating SPI today takes four tools and an agent that knows nothing about the program. The keelson-rib-spi console in Keelson reads the program well. Its 23k lines and 464 tests cover failure attribution, incident folding, the upstream radar and template rollout. But it writes only to GitHub, and only through board buttons. Stack work happens in a terminal with spi, kubectl and az, and GitLab upstream work in glab or the browser. Rerun-when-deployable waits and workflow approval pauses are lost on restart. Setup means installing Bun, Keelson and seven command-line tools by hand.

SPI Code is one Electron app with three parts. The first is @spi-code/core, the domain extracted from keelson-rib-spi, which both the rib and the app use. The second is a host process that runs the sweeps and drives Copilot through @github/copilot-sdk, with SPI operator tools running in the host. It records every run, approval and write intent in SQLite, so a restart never loses a wait or repeats a write. The third is a three-pane window: the program tree on the left, a console view or an agent thread in the middle, and an inspector on the right. The app installs, versions and signs in the tools it needs, without Homebrew or a terminal.

SPI Code supports one agent provider and has no MCP server, CLI or plugin system. Threads come in two kinds. In an operate thread, Copilot has no shell and no file access, and every command it can cause is a typed tool with a declared tier. In a code thread, Copilot reads and edits files in an app-owned worktree, and each command it wants to run is approved on its own card and runs in an OS sandbox with no credentials. SPI Code itself makes the commits and the push, and the push is an approval card too. Fixes on a fork's main branch can still go to the Copilot coding agent. Linux is not a target. SPI Code does not replace the spi CLI or the fork workflows, and it never stands in for a human review gate. Its picture of the environment is no stronger than its evidence. Every view says when a source is unread, and a write that needs a deployable environment is refused while evidence is missing or in conflict.

Threads anchor to objects

Every thread has an anchor: the program, a branch, a service line, the stack, a queue item or a PR. The anchor decides three things:

  • Copilot's starting context: the object's readItem text (title, cause, effect, next action, related items) and the sweep time it came from.
  • Where the thread is listed in the tree.
  • Which operator tools are offered first. Every tool stays reachable.

Typing in the composer on a console view starts a thread anchored to whatever is selected.

Thread kinds

A thread's kind is set when it starts and shown in its header. An operate thread reads the program and proposes typed tools; Diagnose a failure runs as one. A code thread works in a worktree on one fork branch (see Code threads). The kind decides the session's availableTools, so Copilot in an operate thread has no file or command tool to call. When a thread already owns a piece of work, every view that shows the work opens that thread instead of offering to start another: the queue row reads "Fix awaiting push", and the inspector's primary action is "Open thread".

One approval, several places

Every approval card has one id and one state in the host's approval store: pending, binding failed, executing, applied, not applied, unknown, declined or invalidated. It shows where it was requested and in the Approvals tab, which is one inbox with the same count on every screen. The decision happens in one place per origin. A card requested in a thread is decided in that thread's composer strip, and its timeline entry and inbox row point there. A card requested by a button is decided on the card itself, in its run and in the inbox. A button never writes: it creates the card, and the card holds the decision.

Process model

SPI Code is Electron. Like T3 Code, it splits a thin main process from a separate backend, adjusted for an app that is never served remotely. The host runs as an Electron utilityProcess and talks to the window over a MessagePort with zod-validated messages. There is no local network port, so nothing else on the machine can reach the agent. M0 measures the Copilot runtime and node:sqlite inside a utility process on signed builds. If either misbehaves, the host becomes a Node child process started with ELECTRON_RUN_AS_NODE, as T3 Code runs it. Only the chosen model is built after M0. The message contract is the same either way.

The window never runs a command and never calls the network. The host pushes it derived view models (briefing, view rows, inspector text), never raw Facts. Every button becomes a host request that passes the same policy check as a Copilot tool call.

Closing the window leaves SPI Code in the menu bar on macOS and in the tray on Windows while any run or wait is open. Quitting with open runs asks first. Waits resume on the next launch, and a single-instance lock stops two hosts from sweeping or writing at once. If the host crashes, main restarts it once. The window then resubscribes from its last event cursor, so no run event is shown twice or skipped.

Copilot runtime

The host drives Copilot through @github/copilot-sdk, pinned at a version Keelson's provider already runs (1.0.26 today). The SDK ships its own runtime for each platform in @github/copilot-sdk-<platform>, so the app bundles no separate CLI. Packaging unpacks that platform package from the asar archive and starts it over stdio by explicit path. It never uses the SDK's in-process mode, which loads a native library into the host and conflicts with the hardened runtime. Each architecture gets its own build because only the matching platform package is installed.

Sessions are isolated from anything the operator has set up for Copilot elsewhere. The client runs in empty mode with a base directory under app data, which keeps the operator's ~/.copilot MCP servers, agents, skills and instructions out of SPI Code. Empty mode also means the runtime never sees the operator's existing Copilot login. Instead, each session gets its token from a provider that reads gh auth token, so one gh sign-in covers both tools and a gh auth switch takes effect on the next session. That provider API is marked experimental, so M0 proves it with no client token: start, list models, stream a turn and refresh. If it falls short, the host passes the gh token at the client level instead, and drops the warm client when the credential changes, as Keelson does. The token stays in gh's keychain entry, and no Copilot credential is written under app data. availableTools lists every allowed tool by name: each SPI tool as custom:<name> and no built-in tool at all. Every SPI tool is registered with defer: "never", because with no built-in tool search a deferred tool would be out of Copilot's reach. Copilot never gets a built-in shell, file, URL fetch, memory or subagent tool. In an operate thread it has no file or command tool at all, and when it needs a log or report it calls read_artifact, which reads only files the host itself saved for the current run. A code thread adds the host's worktree tools from appendix C: file reads, search and edits confined to the worktree, run_command and commit. onPermissionRequest denies every kind, so a built-in tool that ever slips through is refused rather than allowed.

SPI tools are registered with the SDK's permission prompt skipped, and the policy check runs inside each tool's handler. The handler is the only place that can hold the target's lock, re-read the binding and write the intent around the actual call. Buttons and playbooks call the same handler, so all three paths share one check. The check runs after the arguments pass the tool's zod schema and before any outside call. Any error in that check, or an answer it cannot read, fails closed. Model choice comes from the operator's Copilot plan, shown as a picker with auto as the default.

Each session starts with a system message seeded from the rib's Watch Officer prompt, followed by the anchor's context and its sweep time. The prompt's rules: read before acting, keep certain upstream changes apart from possible ones, never assume maintenance can be cleared, and name the exact next action. Appendix D lists the session lifecycle hazards Keelson's provider already handles; the host copies those fixes.

Authority and approvals

SPI Code can act in GitHub, GitLab, Azure and the cluster through typed tools, with the operator's own sign-ins. Each tool builds its own command from validated arguments, supports an explicit list of variants, and declares one tier. Outside a code thread's sandbox, no tool runs an arbitrary command. A button press, a playbook step and a Copilot tool call all go through the same check. Copilot proposes. Neither Copilot nor a playbook can approve a proposal.

Each Change and Consequential tool declares its binding: the facts that must still hold when it runs (appendix C). For a merge, those are the head SHA, base SHA, mergeability, required checks, review state and draft state. The merge itself is sent with --match-head-commit, so GitHub refuses it if the head moved after the check. For an environment upgrade, the binding is the declared version, maintenance state, no lifecycle run in flight, and the tenant, subscription and cluster the card names. A recovery tool binds the state it exists to fix. Clearing maintenance makes the same check the lifecycle workflows make before they clear it: no lifecycle run in flight, the deployed ref matches the declared stack version, and spi status reports the environment ready, with maintenance as its only blocker. It does not require the environment to read deployable, because clearing maintenance is what makes it deployable. A pending card does not expire. When the operator approves, the host takes the target's named lock, re-reads every binding field, and runs only if all of them still hold. Otherwise the card says which field changed and nothing runs. Named locks per fork and per environment serialize conflicting writes across threads, playbooks and buttons.

Every call, including a Read, is written to the run log with its arguments, result size and duration. Child processes never inherit SPI_SKIP_GUARD or another guard-bypass variable.

Evidence before a write

Every read result carries the same envelope: its source, when it was observed, whether it is complete, and whether it is fresh, stale, unread or failed. A source is stale when its last good read is older than twice its sweep interval, incomplete when a page or size limit cut the read short, failed when its latest read errored, and unread when no read has succeeded since the app started. Views show that envelope wherever a value is drawn. A write whose binding needs a deployable environment is refused when deployability is unread or when sources disagree, for example when the inferred model says deployable but a live spi status says blocked. The card names the disagreement. Both values stay visible. Neither silently wins. A value drawn only from inferred sources says so wherever it is shown, including the top bar ("Deployable · inferred").

Redaction runs on every result before it reaches Copilot or SQLite. It strips tokens, keys, connection strings and kubeconfig credentials. Pod logs and kubectl get results have size limits, and Kubernetes Secrets have no reader.

Code threads

Some fixes have to land on fork_integration or in files the template owns, where the coding agent cannot work. A code thread makes those fixes in an app-owned worktree. It starts from a finding or an inspector action, checks out the fork at the head the finding read, and carries the finding as context. Each fork is cloned once under app data and shared by its worktrees.

Each code thread commits to its own local spi/* branch and names the remote branch it targets, for example spi/fix-prove-418 → fork_integration. One thread at a time holds the lease to push to a given remote branch. The thread header shows the branch, the target, and the base and head commits.

Command sandbox

Commands run under an OS sandbox: Seatbelt on macOS and a restricted token on Windows. If the sandbox cannot start, the thread offers no commands. Inside it, a command:

  • can write the worktree checkout only. The clone's git folder, hooks and config are read-only to it, which is why SPI Code makes the commits.
  • gets its own home folder and an allow-listed environment, with no GH_TOKEN, GITHUB_TOKEN, AZURE_*, ARM_* or SSH_AUTH_SOCK, and no credential helper.
  • cannot read the keychain, ~/.ssh, ~/.kube, ~/.azure or the gh config.
  • is refused when it is git push, gh, az, kubectl, spi, flux or helm. Those actions go through SPI Code's own tools.

Network access stays on, because Maven downloads dependencies, so an approved command can send whatever the worktree holds. The card shows the exact command for the operator to judge, and Settings states the limit.

SPI Code's own git

Commit, status, diff and push run outside the sandbox. Each of those calls names the clone's git folder directly and never follows the worktree's .git file, which a sandboxed command can write. Each runs with hooks off and repository config ignored. push_branch pushes the exact commit from the fork clone to the remote URL SPI Code holds. The push is fast-forward only and is refused unless the remote is still at the commit the card names. Its binding is read when the card is made and again on approval (appendix C).

Terminal

Each worktree has a terminal drawer with two tabs. The first is a read-only view of Copilot's approved commands and their output. The second is the operator's own login shell in the worktree, outside the sandbox and labelled that way, for rebasing, resolving conflicts and committing by hand. SPI Code re-reads the worktree before it makes any card, so work done in that shell is picked up.

Runs and durability

Everything that does work is a run: a verb pressed in the inspector, a Copilot turn, a playbook, and a wait such as rerun-when-deployable. A run is a row in SQLite with an append-only event list. The window shows a run's log in the right panel and lists active runs and waits in the left bar. Each host write (a push, a re-run, a dispatch) gets a run. Commands and commits stay in their thread's work log.

Before any outside write, the host records an intent: the tool, its exact arguments, the binding it checked, and the facts that will identify the result, such as the dispatch time and actor or the PR number. After the call returns, the intent is closed with its result. If the app stops between the two, the run reopens as outcome unknown. Each write tool declares how to look up its own outcome, for example whether the PR is now merged, or the state of the workflow run the dispatch returned. The host runs that lookup before offering retry and never re-sends a write without one. The lookup ends in one of three states. Applied closes the run. Not applied allows retry, and is reached only on positive evidence that the write did not happen, never because time passed. Unknown keeps the run open, with retry disabled, until a lookup succeeds or the operator records that they checked by hand. Writes that create text on GitHub or GitLab (an issue, an MR, a comment) carry the intent id in a hidden marker, so the lookup finds them exactly. A write to several targets keeps a ledger with one outcome per target and never retries a target that is applied or unknown. A target whose last write by the same tool is unknown is held out of new fleet actions, and named, until the operator confirms the candidate run or not applied is proven. Appendix C gives each tool's lookup. The M4 issue carries the exact fields and the crash-test matrix for every write, and M4 starts from it.

Waits and verb or playbook approvals survive a restart. A wait resumes its condition check on the next sweep. A pending approval card shows again and binds when approved. A Copilot tool call does not survive a restart, because the SDK restores the conversation but not the in-flight call. That call is marked cancelled, and Copilot is told so on the thread's next turn. A command running in a code thread's sandbox stops with the host, and running it again takes a new card.

Playbooks

A playbook is a versioned state machine the host runs as one run. Each step has a stable id and is one of four kinds: a tool call, a Copilot turn with a narrowed tool set and a schema-checked result, an approval, or a wait on a model condition. Every transition is committed before the next step starts. On restart the host reads the last committed transition and continues from there, or reports outcome unknown when the step was a write. A run keeps the playbook version it started with. Playbooks are TypeScript in the app, not user-authored YAML. Version 1 ships two.

SPI Code's own tool processes get a scoped environment. The app's tools come first on PATH, followed by the PATH captured from the operator's login shell, as T3 Code does. That lets an app started from Finder find the same tools a terminal would. Sign-ins use each tool's own flow: gh through the browser (which also signs in Copilot), glab against community.opengroup.org, and az login with the stack's tenant filled in. Tokens stay in each tool's own store or the OS keychain. Commands in a code thread use the sandbox profile instead.

Relationship to Keelson

The SPI domain moves into @spi-code/core, a package in the SPI Code repository, in two steps. M1 moves the pure parts: Facts, the model, the briefing and readItem. M2 moves the collectors and action planning behind an exec port, once the host actually calls them.

The package has no Keelson, Bun or Electron dependency:

  • Fleet membership, rollout policy, configuration and the clock are passed in as arguments, not read from module globals.
  • Bun.YAML is replaced by yaml.
  • Board tone types stop leaking into the model.
  • The package ships compiled JavaScript.

The rib depends on a release tarball of core and becomes a thin adapter. It keeps its boards and Keelson lifecycle, so the Keelson tab keeps working.

The domain tests move into core and switch from bun:test to vitest, a mechanical change. The board and adapter tests stay in the rib. The M1 check is that all the moved tests pass and the live Keelson tab renders the same Today on the same sweep. Core lives in SPI Code's repository because, from M2 on, the host is what drives its changes. The rib pins a core version and bumps it only when asked. Two sweepers would share one GitHub GraphQL budget. So from M2, the rib's sweep is off by default and its tab reads the last Facts it recorded. Once M4 ships, the rib's verbs are switched off too, so two hosts can never pace or dispatch the same fleet action. The rib retires after SPI Code has been used daily for a release cycle. That decision is made then.

From Keelson, SPI Code takes the Shore tokens and the palette validator as code. It uses Keelson's Copilot provider as the reference for session handling and tool projection. It takes three ideas as concepts: verbs that return a client effect (open the inspector, open a run, start a thread), durable runs with cursor-read events, and the shapes of investigate and plan-act-evaluate. From T3 Code it copies, under MIT with the notice kept, the login-shell PATH capture, the verified app-owned installer, the readiness states, the semantic theme roles, the right-panel tab model and the electron-builder signing setup. It adapts T3 Code's work log, diff view, terminal drawer and composer approval strip for code threads.

Milestones

Each milestone ships something the operator uses. M0 and M1 run in parallel because neither depends on the other. Validation

Core keeps the rib's fixture tests. They cover attribution, incident folding, pacing, release naming and briefing wording, and run on every change. The host is tested against recorded Facts replays, so a sweep can be reproduced without touching GitHub.

The agent runtime is tested against a fake SDK session that scripts tool calls. Those tests check three things. Every tier answers the way the table says. A tool missing from availableTools cannot be reached. A policy error refuses the call.

Durability tests stop the host at each crash boundary: before an intent is written, after it is written but before the call, and after the call but before the result. Each test checks what the run reopens as.

Sandbox tests run commands that try to read each blocked path, write the clone's git folder, add a hook, set a config value and repoint the worktree's .git file, then check that SPI Code's commit and push ignore all of them. Push tests move the remote between card and approval and expect a refusal.

A packaged-app smoke test runs on macOS and Windows in CI. It starts the app, completes a scripted Copilot turn against a stub model, and screenshots each view in both appearances.

D · Copilot session checklist

BehaviorHandling
Disconnect is asynchronousWait for the previous session to release before resuming it, as Keelson's waitForSessionRelease does. Resuming early closes the new session.
Resume ignores model and effortCall session.setModel after every resume.
Warm clients are sharedCount references, so a retry on one thread never stops a client another thread is streaming on.
Connection errorsMatch the SDK's connection errors, restart the runtime and resume the session; the in-flight tool call is marked cancelled.
Operator's own Copilot setupempty mode and an app-owned base directory; availableTools on every session.
Sign-in under empty modeEmpty mode sees no existing login and would store a new one in plain text. Each session takes its token from a provider that reads gh auth token, so an account switch is followed. The provider API is experimental and is proved in M0. The fallback is a client-level token with the warm client dropped on a credential change. Setup checks the account has a Copilot seat with a real session probe.
Thread kindsavailableTools is set from the thread's kind when the session starts. A code thread's session includes the worktree tools; an operate thread's never does.
Tool deferralRegister every SPI tool with defer: "never"; with no built-in tool search, a deferred tool cannot be reached.
SDK upgradesRun the fake-session suite and the packaged smoke test on both platforms before the pin moves.

F · Alternatives not chosen

AlternativeWhy not
Fork T3 Code and strip itAbout 650k lines built for many providers and remote use, with heavy upstream churn and Effect throughout. Every package is private, so nothing can be depended on. The strip would touch contracts, settings and onboarding across the tree and leave conceptual weight the app never uses.
Tauri or a Swift and WinUI appThe domain, the Copilot SDK and the rib's tests are TypeScript on Node. Tauri would still need a Node sidecar for them, and two native UIs would double the window work.
Copilot through ACP, as T3 Code doesCopilot CLI accepts client tools over ACP only as an MCP HTTP server. The SDK registers tools in the host, with no server to secure.
Host as a localhost WebSocket serverOnly needed for remote clients. A MessagePort gives the same separation with no port and no token.
Port Keelson's YAML workflow engineIt is bound to Bun, and its approval pause does not survive a restart, the property playbooks need most. Two typed state machines on the run store are smaller than the port.
A general command toolA wrapper, interpreter or script defeats any classification by binary and verb. Typed tools with explicit variants are the only way the tier table can be enforced. Code threads run commands only inside the sandbox, one approved card each, with no credentials.
Copilot built-in file reads with path limitsThe callback does see read paths, but a path allowlist for Copilot's own reader would be a second file policy beside the tools. read_artifact keeps one boundary: only files the host saved for the run.
Extract core inside the rib repositoryFrom M2, the host drives core's changes. Keeping core in the rib would put every host change behind a rib release.
Copy the domain into the app and retire the rib nowLoses the live tab as the check that nothing changed, and leaves two diverging copies.
Code changes only through the coding agentThe agent opens PRs against main, so it cannot take fork_integration conflicts or template-owned files. Those fixes would leave the app for a terminal.
A command allowlist by nameOnce a command starts, it and its child processes run whatever they like, so a name check proves nothing. The sandbox and the credential-free environment hold for every process a command starts.
Commands with the operator's environmentDefault config files, the keychain and the SSH agent would give every approved build the operator's GitHub, Azure and cluster access.
Merging cascade PRs in the appGate 2 is a human review on GitHub. merge_pr covers Dependabot and template PRs only.
Homebrew and WinGet installsA clean Mac has no Homebrew, and WinGet can need elevation. uv covers Python, az and spi on both platforms without either.
Several palettes with a pickerOne palette in two appearances covers the need. The role model leaves room for more later at no cost now.

G · Risks

RiskHandling
Copilot runtime in a signed, packaged appProved in M0 on a notarized build before anything depends on it. A Node child process is the fallback for the host.

Rib and app both actingThe rib's verbs are switched off at M4. Both pin the same core version, and the rib carries no domain logic.
