# spicode-xia.12 Copilot command ownership on macOS

The Copilot SDK 1.0.26 did not provide a command ownership handle SPI Code could use after both the host and runtime died. A marked foreground `sleep 600` survived `SIGKILL` of both processes. A fresh host process cold-resumed the same Copilot session, attested Seatbelt again, and invoked `stop_bash` with the original shell ID. The original sleep still ran.

The probe ran on macOS 27.2 (26B123), arm64, with Node 22.22.0 and the built host's `openSandboxedThread`. A disposable clone, workspace, thread temp and app data directory held only fixtures. The probe approved the exact native `bash` invocations through `session.rpc.tools.execute`, kept the GitHub credential in memory and reported only identities and sanitized observations. Each sleep had a unique argv marker. The launcher and runtime also had unique command lines. The harness checked the marker, PID and microsecond start time before sending individual cleanup signals. Every scenario kept a separate decoy sleep alive through the stop or restart, then removed all of its own processes, including the decoy.

| Native `bash` command shape | SDK `session.abort()` | Both processes killed, then the same SDK session cold-resumed |
| --- | --- | --- |
| Foreground marked `sleep 600` | Ended | Sleep and its shell survived. The shell's parent became PID 1. |
| Marked `sleep 600 & wait` | Ended | Sleep and its shell survived in the original group and session. |
| Background sleep with its descriptors redirected, then normal shell exit | Sleep was already reparented to PID 1 and survived | Sleep survived in the original group after its leader exited. |
| Background helper calling `setsid()` and then `exec`ing the marked sleep, while the command waited | Sleep moved to a different group and session, then survived after reparenting to PID 1 | Sleep survived in its new group and session. |
| Same `setsid()` helper with a normally exiting shell | Bash returned success. The sleep was already under PID 1 at the first observation and survived. | Sleep survived under PID 1 in its own group and session. |

`proc_pidinfo(PROC_PIDTBSDINFO)` and `getsid()` confirmed that a foreground Bash launch was a direct runtime child and the leader of its own group and session. For example, the restart probe saw sleep PID 19432 start at `1795140196.715619`, with parent, PGID and SID all 19430. After restart, those values were unchanged and parent 19430 had been reparented to PID 1. The SDK's model-turn `tool.execution_start` and Seatbelt `spawn_completed` events carried a tool call ID with neither an OS PID nor a start time. `shellToolInfo` reported path hints and `shellExecution` reported the exit code. The probe could match survivors with its deliberately retained markers. Arbitrary commands control their own arguments and can leave the original ancestry, group and session. A process snapshot after that point cannot prove the survivor belonged to the command. An unaccounted-for descendant would have to read `not known`.

The separate `shell.exec` RPC confirmed the SDK's documented process-group gaps (`dist/generated/rpc.d.ts`, `shell.exec` and `shell.kill`). Its nonnumeric `processId` handled `shell.kill` while the runtime was alive. A background child still in the group ended. A child that called `setsid()` survived even when `killed` was `true`. After a normal shell exit, `shell.kill` returned `false` and the background child survived. The original `processId` also returned `killed: false` after cold resume while the marked foreground sleep was still running. This RPC is separate from the model's built-in Bash tool.

| Additional live check | Observation |
| --- | --- |
| Timed-out command output | An 800 ms `shell.exec` timeout ended a marked same-group background sleep while the runtime remained up. That host RPC took no model turn and fired neither post-tool hook, so there was no model-facing output from that timeout. Built-in Bash exposes `initial_wait`, which the SDK describes as a wait for output rather than a termination deadline. In a separate signed-in turn, the model passed `initial_wait: 1` while the command printed a synthetic marker and slept ten seconds. The recorded tool call completed successfully after ten seconds, the success hook redacted the marker, and the model reported seeing the redaction. A hard timeout on the model's Bash path was not observed. |
| Stopped model command output | A signed-in model invoked Bash, printed a synthetic token-shaped marker from a fixture, then started the marked sleep. Aborting the turn ended the sleep. Neither post-tool hook fired, the session recorded no completion result for the tool call, and there was no subsequent model reply in the stopped turn. |
| App data reads | The confined Bash tool could read the positive control in the worktree. It could neither open disposable `appData/kube/config` and `appData/azure/probe` fixtures nor list `appData/azure`. The probe discarded command output and reported exit status only. |
| Environment nonce sweep | With SIP on, `/bin/sleep` and `/bin/sh` hid their environment from a same-user reader through both `ps eww` and `KERN_PROCARGS2`. A hardened-runtime Node process showed its marker. An environment nonce sweep cannot find those Apple binaries by their nonce. |
| MXC command ownership | Source inspection showed that `mxc.spawn` returns a handle with `kill()` and no PID. What `kill()` ends and what survives a host `SIGKILL` are unread. |

A failed built-in result bypasses the host's model redactor because the SDK failure hook cannot replace it (spicode-xia.6 review, ruling T6). The stopped-turn observation above is narrower: this call produced no completion result to redact. The observations here came from the live SDK. This investigation added no replay fixtures or runtime-sequence tests.

**Decision for the maintainer:** Keep spicode-xia.11 edits-only. Revisit commands when the runtime can provide a durable, command-scoped process identity and a verifiable termination path, or after a separately approved host-owned confinement design proves those properties. Stop this bead at the probe finding. The probe did not implement startup cleanup or test an SPI Code journal result of `cancelled`. Windows remains uncovered pending spicode-xia.17.
